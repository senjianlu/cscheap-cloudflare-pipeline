# 0002:内容单元 = 公共信封 + 类型注册表;取值集合来自使用方配置

- 日期:2026-11-19
- 背景:文章、wiki 条目、文档页要走同一条发布流程,由不同的渲染端读取;还有一类由其他系统同步进来的实体
  不在 Git,却要能被内容引用。各类型的专属字段差别很大,而审核状态、作者、标签、SEO、图标这些元数据是共通的。
  本仓是公开仓,不能写死任何使用方的语言、频道或域名。
- 决定:
  - 每个内容单元是一份语言无关的 `item.json`(公共信封)加若干 `<locale>.mdx`。信封字段对所有类型相同,
    类型专属数据放在 `data`,由该类型的 schema 校验。原则:能翻译的进 frontmatter,不能翻译的进 `item.json`,
    能算出来的只进数据库。否掉「每个类型一套独立结构」(共通字段各写一遍,跨类型查询无从统一)。
  - 一张类型注册表登记每个类型的来源(`git` / `sync`)、正文模式(`required` / `optional` / `none` / `generated`)、
    `data` 与 `l10n` 的 schema、被提升为必填的信封字段、默认图标。同步类实体只登记类型键与引用键格式,
    不经本仓校验,数据与表结构归同步方。
  - 类型对信封字段的「提升必填」在类型组合后的 Zod 结构里表达,不用事后的校验函数,这样每类型的 JSON Schema
    带同样的必填约束。否掉「留在自定义校验里」(只用 JSON Schema 的编辑器与其他语言实现会放过缺字段的单元)。
  - 与语言、频道、参与者、外部资源域名有关的取值集合全部来自使用方的 `site.json`,由 `createContract(site)` 生成
    带上下文的契约;JSON Schema 在这些位置只输出格式约束。频道名与「哪个 stage 进哪个频道」也由配置决定。
  - `stage` 五态与只追加的 `workflow` 沿用现有文档仓已在用的审核流,使各内容仓是同一套流程。
  - 图标用引用:字符串是 Lucide 图标名,只校验格式、不设受控清单;也支持图片图标。`false` 表示不显示,
    不写表示用类型默认。
  - 标签、分类、作者走受控词表;缺译文的语言不出页;语言标签用 BCP 47 并要求规范大小写。
  - Zod 是唯一事实源,JSON Schema 由它生成并入库;表达不了的规则只在 Zod 侧校验,清单列在
    `docs/architecture/contract.md` §7。正文 AST 不生成 JSON Schema。
  - 首版类型:`blog.post`、`wiki.site`、`wiki.event`、`wiki.guide`、`docs.page`、`docs.api`,以及同步类型 `item`。
- 影响:新增类型只需在注册表登记并补模板,不需要迁移;任何与使用方取值有关的常量出现在 `contract/` 里都是缺陷
  (由 AGENTS.md 的「使用方无关」「公开仓卫生」规则与评审约束,不设机器扫描);只依赖 JSON Schema 的实现必须知道 §7 列出的规则需要另行实现。首批使用方接入前不打 tag,
  契约可无迁移调整;接入后破坏性变更升主版本。
